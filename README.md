# 多智能体 RAG-ReAct 协作系统

一个从零手写、**逐行注释**的教学项目，用一份代码同时演示 **RAG**、**ReAct** 和 **多智能体（Multi-Agent）** 三项技术。

**零外部依赖**（只需 numpy），**离线可跑**（默认使用 MockLLM），**不需要 API Key**。

---

## 一、这个项目解决什么任务

用户输入一个技术问题：

> 我们是一个 5 人左右的小团队，想搭建一个中文企业知识库问答系统，没有专职运维人员，预算也比较有限。请问应该怎么选择向量数据库和相关技术方案？

系统产出一份**带引用来源的选型报告**，并在这个过程中展示：

- **RAG** —— 从本地知识库检索带来源的资料
- **ReAct** —— 每个 Agent 内部都是 Thought → Action → Observation 循环
- **Multi-Agent** —— 调研员 / 分析师 / 撰写者 / 审校者分工协作，审校可打回重做

为什么选这个任务？因为它天然具备三个特征：**有知识依赖**（必须查资料）、**需要多步查证**（边想边做）、**工作可切分**（找资料/分析/写作/审校是不同认知模式）。三者正好对应要演示的三项技术 —— 不是硬凑的。

## 三、为什么要有 MockLLM（重要）

调试多智能体系统时，真正难的不是「模型聪不聪明」，而是**流程对不对**：

- ReAct 循环有没有正确解析出 `Action` / `Action Input`？
- Critic 打回后，Orchestrator 有没有真的重新派活？
- 黑板上的数据有没有被下游 Agent 正确读到？

**这些全是工程问题，和模型无关。** 用真 API 调试的代价是：花钱、慢、输出不稳定（这次能跑下次崩，你分不清是代码错还是模型抽风）、没 Key 的人根本跑不起来。

`MockLLM` 用规则代码模拟模型输出：固定输入 → 固定输出，零成本、不需要网络。代价是它不会真推理，所以只能验证**流程正确性**，不能验证**报告质量**。

**建议的学习路径：**

1. 用 MockLLM 把全流程跑通，看日志、打断点，彻底搞懂数据怎么流
2. 切到真实模型，观察同样的代码在真模型下行为有何不同

## 五、可视化是怎么实现的（值得单独讲）

网页可视化不是「另写一套」，而是**在原有埋点上加了一层消费者**。这个设计本身很有借鉴意义。

### 关键改动：把日志器改造成发布-订阅

原来 `TraceRecorder` 只干一件事：把事件写进 `trace.jsonl`。

做 Web 时最直接的想法是再写一个 `WebTraceRecorder` 类专门推送。但那意味着：

- 所有埋点要写两遍（一处落盘、一处推送）
- 以后加新事件类型，两处都要改，**必然漏一处**
- 埋点代码散落各处，越来越难维护

所以改成了发布-订阅：

```python
# 埋点处只调用一次，不需要知道有谁在消费
tracer.record_react(agent="researcher", step=1, phase="thought", content="...")

# 记录器内部再分发给所有订阅者
tracer.subscribe(broadcast)   # Web 模式：推给浏览器
                              # （落盘是内置的，不需要额外订阅）
```

**收益**：业务代码一行都没改，就同时获得了「落盘」和「实时推送」两种能力。
以后想推给 WebSocket、发给监控系统，只需再 `subscribe` 一个回调。

> 这是观察者模式在可观测性场景下的典型价值：**让「产生事件」和「消费事件」彻底解耦**。
> 本项目里这个模式出现了两次（黑板通知订阅者、tracer 通知订阅者），说明它在「一对多通知」下确实好用。

### 为什么要用队列做缓冲

跑任务的线程和推送的线程是两个线程。MockLLM 是毫秒级的，产生事件的速度可能远超浏览器消费速度。

如果直接推，**慢客户端会阻塞任务线程** —— 业务被可视化拖慢，这是绝对不能接受的。

所以中间加队列：任务线程只管往队列里塞（永不阻塞），推送线程按自己的节奏取。
每个浏览器连接有自己独立的队列，互不干扰。队列满时**丢弃新事件而不是阻塞**。

> 可观测性永远不能反过来影响业务 —— 这是铁律。

### 为什么用 SSE 而不是 WebSocket

| | SSE | WebSocket |
| --- | --- | --- |
| 方向 | 单向（服务端→浏览器） | 双向 |
| 底层 | 普通 HTTP | 独立握手协议 |
| 重连 | 浏览器自动重连 | 需自己实现 |
| 依赖 | Flask 原生生成器就够 | 需要额外库 |

我们的需求是**纯单向**的：服务端推事件，浏览器只显示。用户交互（启动任务）用普通 POST 就够了。

**选能满足需求的最简单方案。** 多引入一个 WebSocket 库，就多一份依赖、多一份部署复杂度、多一类出错可能 —— 而它带来的双向能力根本用不上。

### RAG 埋点：依赖注入的实际应用

要展示「为什么这个块被选中、那个被阈值刷掉」，就必须在 `rag/store.py` 内部埋点。但 rag 层不该知道 agents/trace 的存在。

所以 `VectorStore` 提供的是**扩展点**，而不是直接依赖：

```python
store = VectorStore(trace_hook=rag_hook)   # Web 模式：上报
store = VectorStore()                       # 命令行：None，零开销
```

依赖方向保持「上层依赖下层」，没有反向依赖。

## 七、项目在实测中踩过的坑（最有价值的部分）

这个项目不是「一次写对」的。下面每个问题都是实际跑出来的，代码里对应位置都有详细注释。**这些问题比代码本身更有学习价值。**

### 1. RAG 检索质量：从 Recall@5 = 0.591 到 0.909

最初只做了稠密向量检索（哈希向量 + 余弦相似度），实测问题严重：

| 阶段 | Recall@5 | 问题 |
| --- | --- | --- |
| 初版（3-gram 哈希向量） | 0.591 | 相关文档相似度只有 0.19，排序混乱 |
| + 多粒度 n-gram | 0.591 | 命中率没变，噪音变多 |
| + IDF 加权 | 0.591 | 分数被拉开，但仍无法过滤噪音 |
| + BM25 混合检索 + RRF | 0.955 | 召回大幅提升 |
| + 双阈值（绝对 + 相对） | 0.955 | 排序质量改善，MRR 提升 |
| + 只让长 n-gram 参与打分 | 0.909 | **噪音查询从 90% 降到 20%** |

**最关键的一课**：我原本想用一个 BM25 绝对分数阈值来判断「检索是否有意义」，但实测发现：

```
相关查询   BM25 最高分区间 19.8 ~ 101.1
无关查询   BM25 最高分区间  9.2 ~  32.3
         ↑ 两个区间完全重叠，不存在能分开它们的阈值
```

深挖发现噪音来自**单字和 2-gram**（"今天晚饭吃什么"里的"天""吃""什""么"在技术文档里到处出现）。解决办法不是调阈值，而是**换一个区分度更高的特征** —— 只让 3-gram 及以上参与打分。

> **当两个分布的取值区间重叠时，不要去调阈值。** 那是在用一个标量区分两个本质不同的东西，注定失败。正确做法是换特征。这是做检索和机器学习时最核心的直觉之一。

（后来为了召回又调回 2-gram，改由 IDF 加权的绝对阈值兜底 —— 见下面第 2 条。）

跑这两个脚本可以复现整个过程：

```bash
python eval_retrieval.py    # 测 Recall@5 和 MRR
python tune_threshold.py    # 扫描阈值，看召回与噪音的权衡曲线
```

### 2. 过滤规则和阈值必须联合调，不能分开调

我一开始把「n-gram 长度过滤」和「BM25 阈值」当成两个独立开关分别调，结果反复在两个极端之间摇摆：过滤调严 → 召回崩；过滤放松 → 噪音多。

**正确做法是联合搜索**：先确定可量化的目标（Recall@5 和噪音率），再一起调这两个参数。`tune_threshold.py` 就是干这个的。

### 7. 切块把词切成两半（可视化才暴露出来的问题）

做网页「引用溯源」功能时，点开引用看到的原文是这样的：

```
01_vector_db_overview#7  ->  "lvus 是独立部署的分布式系统…"     ← Milvus 的 Mi 被切掉了
01_vector_db_overview#2  ->  "hbor）算法。它不保证找到…"        ← Nearest Neigh 被切掉
01_vector_db_overview#1  ->  "个向量"，这是一个高维空间…"       ← 前引号被切掉
```

**根因**：overlap 的实现是 `current[-chunk_overlap:]` —— 无脑按字符数截取。

**为什么这是个真问题，而不只是「不好看」**：

1. **检索质量**：碎片会产出无意义的 n-gram（`lvus`、`hbor`），污染倒排索引，还可能产生虚假匹配
2. **溯源体验**：看到 `lvus` 会让人怀疑数据是不是坏了
3. **引用可读性**：报告引用这种块，读者无法判断上下文

**修正**：从「截取 N 个字符」改成「截取后向右对齐到最近的语义边界」（段落分隔 / 句末标点 / 空白 / 中英文交界）。

> **这个 bug 已经存在很久了** —— 它在命令行模式下完全不可见，因为没人会去逐块打印原文。
> 是「点击引用看原文」这个可视化功能把它逼出来的。
>
> **这就是可视化的真正价值：它不只是把已有信息画得好看，**
> **而是创造了一个新的观察角度，从而暴露出你原本看不见的问题。**

修正后检索质量还略有提升（MRR 0.788 → 0.792）。

### 8. 事件被贴上了错误的类型标签

RAG 埋点写好后，网页的检索面板**一直是空的，而且没有任何报错**。

排查发现：我把 `tracer.record_event` 直接当成埋点回调传了进去。它看起来完全合理 —— `record_event(**detail)` 正好能收下埋点数据。

但它生成的是 `kind="event", event="rag"`，而前端期望 `kind="rag"` 才是检索事件。**事件确实发出来了，只是被归到了错误的类别里。**

`record_event` 的语义是「记录一个里程碑」，而检索埋点不是里程碑，是结构化的过程数据。

> **教训：复用函数前要问「它的语义和我需要的一致吗」，而不只是「参数能不能传进去」。**

这个 bug 是 `test_web_pipeline.py` 抓出来的 —— 它直接断言「必须收到 recall/fuse/prune/final 四类埋点」。
如果只靠开浏览器肉眼看，你只会看到「面板是空的」，很难判断是前端渲染问题还是后端根本没发。

### 3. 安全检查静默失效（最危险的一类 bug）

引用提取的正则我最初写成：

```python
r"\[([A-Za-z0-9_\-]+#\d+)\]"     # 只允许英文数字下划线
```

结果编造的引用 `[99_不存在文档#7]` **完全没被匹配到**，程序化防幻觉校验报告 `invalid=[]` —— 编造引用被顺利放过。

**这个 bug 的可怕之处**：校验器不报错，只是什么都没查到，看起来像「一切正常」。如果没有 `test_hallucination_guard.py` 这个回归测试，它会一直潜伏到线上。

修正：字符类改为反向排除 `[^\[\]#\s]+`。

**并且**：同样的正则我在四个文件里各写了一遍，修一处漏三处。所以提取成了 `agents/base.py` 里的 `CITATION_PATTERN`。

> **消除重复不是为了代码好看，而是因为重复会让修复变得不可靠。**

### 4. 分类判据不能用「内容里有什么」，要用「结构骨架」

MockLLM 需要判断「当前该演哪段剧本」。我用 `"sub_tasks" in prompt` 判断「这是规划任务」，结果**所有角色都被误判成规划任务** —— 因为 Orchestrator 把任务规划的 JSON（含 `sub_tasks` 字段）通过 context 传给了下游 Agent，规划内容出现在每个 Agent 的 prompt 里。

**正确判据是框架生成的段落标题**（`## 工具调用格式（必须严格遵守）`），这些不会被业务内容污染。

> **判据要选「由生产者严格控制的、结构化产生的」特征，而不是「可能出现在任何地方的自由文本」。**

### 5. 两条执行路径行为不一致

`BaseReActAgent` 有两条路径：走 ReAct 循环的、不走循环单次生成的。我在前者里调了 `postprocess`，在后者里忘了。

后果：Writer 不把草稿写进黑板 → 最终报告 0 字符；Critic 不把结论写进黑板 → 永远判定为 revise。**整个流程不报任何错**，只是结果全空。

> 给一个类加分支时，要把所有「公共收尾动作」抽出来，确保每条分支都执行。

### 6. 赋值顺序 bug

`Message.FINAL` 的 payload 里用了 `result.summary()`，但我把这条 post 放在了字段赋值**之前**。结果消息显示「0 轮 | 黑板消息 0 条 | 报告 0 字符」——全是初始值。数据都算好了，只是读取时机比写入早。

### 7. Windows 控制台编码

Windows 中文控制台默认 GBK，打印 emoji 直接 `UnicodeEncodeError` 崩溃。解决方式不是改系统设置（换台机器又不行），而是在程序启动时把 `stdout/stderr` 重新包装成 UTF-8，并且用 `errors="replace"` 保证「显示难看」远好于「程序挂掉」。

见 `core/console.py`。

## 八、核心设计决策（为什么这么写）
### 为什么所有 Agent 共用一个 ReAct 引擎？

常见误区是给每个 Agent 写一套独立的循环逻辑 —— 结果得到 5 份高度相似但细节不同的代码。本项目让 `BaseReActAgent` 负责「怎么想」，子类只定义「想什么、能做什么」。

**这会让你发现：多智能体并没有那么神秘。** 它本质上是「同一个推理引擎 + 不同的角色设定 + 不同的工具权限」。真正困难的部分不是「让 Agent 会思考」，而是**角色怎么划分、信息怎么传递、质量怎么保证**。

### 为什么用黑板而不是直接调用？

直接调用（`orchestrator` 拿 `researcher` 的返回值传给 `analyst`）的问题：强耦合、无法并行、难以追踪、加新角色要改所有调用点。

黑板模式的价值：解耦（Agent 只依赖消息格式，不依赖谁生产的）、可追踪（每条消息留痕）、可扩展、可并行。

### 为什么 Orchestrator 不走 ReAct 循环？

因为它的工作是**确定性的流程控制**（拆解 → 派活 → 审校 → 返工判定）。用 ReAct 循环让 LLM 自己决定下一步会有三个问题：不确定、可能漏掉必需环节、成本更高。

**混合做法**：主流程用代码固定（可靠、可控、可调试），任务**拆解**用 LLM（需要理解用户意图），**返工判定**用代码读结构化结论。

> **不要因为「用了 LLM」就以为所有决策都该交给 LLM。** 把确定性的事情用代码写死，把不确定的事情交给模型。

### 为什么 Critic 要分两层校验？

| 层级 | 手段 | 特点 |
| --- | --- | --- |
| 第一层 | 程序化校验（集合运算） | 100% 可靠，不会出错 |
| 第二层 | LLM 评审 | 能理解语义，但会出错 |

**只用 LLM**：它不擅长核对精确的 ID 字符串，会漏掉明显的编造引用。
**只用程序**：无法判断「对比维度够不够」这类需要理解的问题。

而且**程序化校验拥有否决权** —— 如果代码发现了编造引用，无论 LLM 说 pass 还是 revise，都必须改成 revise。确定性的证据优先于模型的判断。

### 为什么角色要按「认知模式」划分？

不是按「步骤」分（那只是把串行流程切成三份，没增加任何能力），而是按**思维模式的冲突**分：

- Researcher：**发散**，宁可多找不可少找
- Analyst：**收敛**，必须做减法聚焦结论
- Writer：**表达**，面向读者组织
- Critic：**怀疑**，主动找漏洞

这四种模式相互冲突。让一个 Agent 同时具备冲突的思维模式，效果一定打折（要么一直发散没结论，要么过早收敛漏信息）。

> **判断标准**：如果两个角色的工作能合并到一个 prompt 里而互不干扰，那就不该拆开。拆分是有成本的。

### 为什么工具参数只有一个字符串？

参数越多，模型填错的概率越高。所有工具都只接受一个字符串参数，把出错可能性降到最低 —— 这是**为模型的可靠性做设计**，而不是为理论上的优雅。

同理，工具的**错误信息也是 prompt 的一部分**：

```
差的：KeyError: 'doc_03'
好的：未找到文档 doc_03。可用文档有：01_xxx, 02_yyy，请重新选择。
```

后者能引导模型自我纠正。这类设计能显著降低 Agent 的无效循环次数。

## 九、用工具权限实现角色隔离

每个 Agent 只注册它该用的工具，这不只是「prompt 更短」：

| 角色 | 工具 | 设计理由 |
| --- | --- | --- |
| Researcher | `list_knowledge_base`<br>`search_local_docs`<br>`read_doc_section`<br>`extract_key_points` | 不需要 `cross_compare` —— 横向对比是 Analyst 的职责。如果调研员自己对比了，Analyst 就没事可做，架构退化 |
| Analyst | `cross_compare`<br>`extract_key_points`<br>`read_doc_section` | **刻意不给 `search_local_docs`** —— 否则它会自己再查一遍，造成重复劳动，更关键的是「证据」和「分析」会混在一起，Critic 无法区分「这条结论有调研证据支持」还是「分析师自己找的」，引用校验链条就断了 |
| Writer | 无 | 只加工已有信息，不该检索 |
| Critic | 无 | 完全基于已有材料做判断 |

**「发现问题的人不负责解决问题」** —— Analyst 发现证据不足时应如实指出，由 Orchestrator 决定是否让 Researcher 补充调研。这保证了各环节职责清晰、可追溯。

## 十、防幻觉的设计链条

RAG 的价值不只是「查资料」，更重要的是**让每个结论都能被核对**。本项目的防幻觉机制分布在多个环节：

| 环节 | 机制 | 位置 |
| --- | --- | --- |
| 检索 | 分数阈值过滤，宁可返回空也不喂噪音 | `rag/store.py` |
| 检索 | 检索为空时明确提示「知识库未覆盖，请如实说明资料不足」 | `tools/rag_tools.py` |
| 提示词 | 给每段资料编号 `[资料1]`，提供可引用的锚点 | `rag/store.py` |
| 提示词 | 显式允许「不知道」：「资料不足时必须说明，不要凭常识推测」 | 各 Agent 的 `system_prompt` |
| 角色约束 | 调研员只报告真实存在的内容，不补充先验知识 | `agents/researcher.py` |
| 角色约束 | 撰写者不得引入任何新的技术事实 | `agents/writer.py` |
| 校验 | 程序化检查引用 ID 是否真实存在、是否在调研范围内 | `agents/critic.py` |
| 校验 | 程序化校验对 LLM 判定有**否决权** | `agents/critic.py` |
| 兜底 | 上游数据缺失时明确告知，而不是让它带着空上下文硬跑 | `agents/analyst.py` |

回归测试：`python test_hallucination_guard.py`

## 十一、练习建议

按难度递增：

**理解层**
1. 在 `knowledge/` 里加一篇自己的文档，看它如何影响检索结果
2. 改 `config.py` 的 `chunk_size` / `chunk_overlap`，用 `eval_retrieval.py` 测效果变化
3. 把 `CFG.max_revision_rounds` 改成 1，观察「只审一轮」对报告质量的影响
4. 把 `CFG.log_level` 设为 `verbose`，看每次送给 LLM 的完整 prompt 长什么样

**修改层**

5. 给 Researcher 加一个新工具（比如「统计某文档的字数」），注意要同时在 `build_default_registry` 注册
6. 改 MockLLM 的 `_critique`，让它第一轮就判通过，观察流程差异
7. 在 `tune_threshold.py` 里加几个你自己设计的噪音查询，重新标定阈值

**设计层**

8. 新增一个 `fact_checker` 角色，插到 Writer 和 Critic 之间，专门核对数字类事实
9. 让 Orchestrator 支持「并行调研」：把一个大问题拆成几个独立子问题，同时派给多个 Researcher
10. 实现「增量索引」：文档更新后只重建变化的块（参考 `knowledge/10_deployment_ops.md` 里关于内容哈希的做法）
11. 把 `HashingEmbedder` 换成真的 embedding 模型，重新标定所有阈值，对比效果差异

**深入层**

12. 给 Agent 加长期记忆：把历史任务的结论存下来，下次遇到相似问题先查记忆
13. 实现「分层检索」：先让 Agent 看文档目录决定查哪几篇，再精读（提示：`list_knowledge_base` 已经提供了基础）
14. 用 `workflow` 思路把写作-审校循环改成多分支：让两个 Writer 各写一版，Critic 选更好的

**可视化层**

15. 给时间线加**耗时条**：把每个 Agent 的 `elapsed` 画成横向条形，直观看出瓶颈在哪
16. 加一个**"导出这次运行"按钮**：把事件流打包成 JSON 下载，便于对比不同配置的效果
17. 做**并排对比视图**：同时跑 `top_k=4` 和 `top_k=8`，把两条时间线并列显示
18. 把**引用校验结果可视化**：在报告里把"有效引用"标绿、"编造引用"标红（后端 `programmatic_check` 已经有数据了）
19. 加**手动干预**功能：让界面可以暂停流程、手动修改 Critic 的判定，观察流程走向如何改变

> 第 18 条特别推荐 —— 它把「防幻觉」这个抽象概念变成了看得见的东西。

## 十三、已知局限（诚实记录）

这些是「零依赖、离线可跑」这个约束带来的真实代价，务必知悉：

1. **哈希向量不是语义向量**。`HashingEmbedder` 本质是词汇匹配，永远不会知道「向量数据库」和「Vector DB」是同一个东西。要真正的语义能力必须换真 embedding 模型（改 `config.py` 一行）。

2. **没有中文分词**。为了零依赖没引入 jieba，只用字符 n-gram。这让「成本」这类 2 字短查询比较吃力（构不成有效 n-gram）。解决需要分词 + 同义词表。

3. **阈值是针对当前语料标定的**。换语料、换 embedding 模型后必须用 `tune_threshold.py` 重新标定。

4. **MockLLM 不会真推理**。它只能验证流程正确性，不能验证报告质量。验证质量必须用真模型 + 人工评估。

5. **它是教学项目，不是生产系统**。缺少并发控制、权限、持久化、增量索引、监控告警等生产必备能力 —— 这些在 `knowledge/10_deployment_ops.md` 里讨论了，但没有实现。

6. **网页版用的是 Flask 开发服务器**。它明确警告「不要用于生产部署」。
   它能正确处理并发（`threaded=True`），但性能、稳定性、安全性都不适合公网。
   生产环境应该用 gunicorn/uWSGI，并且 SSE 需要额外注意超时配置。

7. **可视化只支持单任务**。一次跑一个，不支持并发队列 ——
   这是刻意的取舍：教学工具不需要任务调度，
   引入它只会让代码复杂度上升而学习收益为零。

8. **工程上任何「零依赖」的选择都有代价，关键是知道代价在哪。**
