# 多智能体系统架构与协作模式

多智能体（Multi-Agent）系统把复杂任务拆给多个各具专长的 Agent，通过协作完成单个 Agent 难以做好的工作。本文说明其架构模式与工程要点。

## 单智能体的能力边界

在决定使用多智能体之前，先要理解单智能体在哪里会失效。

**上下文过载。** 一个 Agent 既要检索、又要分析、又要写作，它的 prompt 里必须同时包含检索指令、分析框架、写作规范、格式要求。这些要求相互干扰，模型很难同时兼顾。表现为：分析做得不错但格式全错，或者格式对了但分析很浅。

**角色冲突。** 写作要求"充分展开、有细节"，而审校要求"精简、挑毛病"。让同一个 Agent 既写又审，它倾向于认为自己写的是对的，审校流于形式。这是一个已经被反复验证的现象：模型很难批判自己的输出。

**注意力分散。** 任务越长，模型越容易丢失早期设定的约束。到生成回答时，它可能已经忘了"必须标注引用"这个要求。

**无法并行。** 单 Agent 只能串行工作，如果任务里有三个独立的子调研，只能一个一个做。

## 核心架构模式

**协调者模式（Orchestrator / Supervisor）** 是最常用也最容易理解的。一个协调者 Agent 负责拆解任务、分派给专业 Agent、收集结果、决定是否返工。专业 Agent 之间不直接通信，都通过协调者。

优点是控制流清晰、易于调试、易于增加新角色；缺点是协调者可能成为瓶颈，且它的判断质量决定整个系统的上限。

**黑板模式（Blackboard）** 让所有 Agent 读写一个共享状态区，没有中心协调者。Agent 各自观察黑板，发现"有自己能处理的工作"就去做。

优点是高度解耦、易扩展、支持并行；缺点是控制流不明确，难以判断"任务是否完成"，容易出现重复工作或死锁。

**流水线模式（Pipeline）** 把任务组织成固定顺序的阶段（检索 → 分析 → 写作 → 校验），每个阶段由一个 Agent 负责。

优点是简单、可预测、延迟低；缺点是无法根据中间结果动态调整路径，灵活性最差。

**层级模式（Hierarchical）** 是多层协调者，适合超大型任务。顶层协调者把任务分给中层，中层再分给执行层。复杂的软件工程类 Agent 系统常用这个结构。

**本项目采用"协调者 + 黑板"混合模式**：Orchestrator 控制流程（协调者的清晰性），Agent 之间通过 Blackboard 交换数据而非直接调用（黑板的解耦性）。这是一个很实用的折中。

## 角色划分原则

角色划分不应该按"步骤"分，而应该按"**认知模式**"分。

反面例子：Agent A 做第一步检索，Agent B 做第二步检索，Agent C 做第三步检索。这不是多智能体，只是把串行流程切成了三份，没有增加任何能力。

正面例子：
- **Researcher**：认知模式是"发散、探索、求证"，目标是把相关信息尽可能找全并标注来源
- **Analyst**：认知模式是"收敛、对比、归纳"，目标是从杂乱信息中提炼出结构化的判断
- **Writer**：认知模式是"组织、表达、面向读者"，目标是把结论变成易读的内容
- **Critic**：认知模式是"怀疑、挑错、找漏洞"，目标是发现前三者忽略的问题

这四个角色的思维方式本质不同，甚至相互冲突（发散 vs 收敛，表达 vs 挑错）。正因为冲突，它们才需要被分到不同的 Agent 里——让一个 Agent 同时具备冲突的思维方式，效果一定打折。

**一个实用的判断标准**：如果两个角色的工作可以合并到同一个 prompt 里而互不干扰，那就不该拆开。拆分是有成本的（额外的 LLM 调用、上下文传递开销、协调复杂度）。

## 通信机制设计

**消息格式必须结构化。** 自由文本消息在 Agent 之间传递会迅速失控：上游写得随意，下游解析困难。应该定义明确的消息类型（任务、结果、审校意见、返工要求），每种类型有确定的字段结构。

**共享状态优于消息传递。** 让 Agent 通过读取共享状态获取需要的上下文，比把上下文塞进消息里传递更好，原因有三：一是避免重复传递大块数据；二是任何 Agent 都能看到全局状态，便于做全局判断；三是状态有版本历史，便于回溯和对比。

**关键是要区分"数据"和"通知"。** 数据放在共享状态里（Evidence、Analysis、Draft），消息只用来传递"事件"（任务已派发、结果已提交、审校未通过）。这样消息很轻量，而重数据只在需要时从状态里读取。

## 质量闭环：Critic 的价值

多智能体相比单智能体最实在的增益，往往不是"分工带来的效率"，而是"**引入独立审查视角**"。

单 Agent 写完就结束了，没有任何检查环节。多 Agent 架构里可以插入一个 Critic，它的职责是：

- 检查每个结论是否有引用依据（防幻觉）
- 检查是否满足既定的验收标准（覆盖度、维度数量）
- 检查逻辑是否自洽（前后是否矛盾）
- 给出可执行的修改建议，而不是笼统地说"不够好"

Critic 的输出必须是结构化的（verdict / score / issues / suggestions），因为程序要根据它决定流程分支：通过则结束，不通过则带着修改意见打回相应 Agent 重做。

**这个打回循环是多智能体架构里最有价值的部分**，也是最需要仔细设计的部分：必须有轮次上限（否则可能无限循环），必须把修改意见明确传递给重做的 Agent（否则它不知道改什么），最好保留历次版本（便于对比改进效果）。

## 工程实践的坑

**坑一：Agent 数量过多。** 每增加一个 Agent，就增加一次 LLM 调用、一层信息损失（上下文在传递中被压缩或歪曲）、一处可能的失败点。超过 5~6 个角色的系统通常难以调试。建议从 2~3 个角色起步。

**坑二：信息在传递中失真。** Agent A 的输出经过摘要传给 Agent B，B 再输出给 C，到 C 时原始信息已经损失大半。解决方案是让 Agent 直接读取共享状态里的原始数据，而不是读上游的摘要。

**坑三：成本失控。** 5 个 Agent 各跑 5 轮 ReAct，就是 25 次 LLM 调用，再加上返工重做，轻松上百次调用。必须在架构设计阶段就估算成本，并设置总预算上限。

**坑四：难以调试。** 分布式的问题最难查。必须记录完整的消息流水和每步推理轨迹，否则一个失败案例要花几小时才能定位。可观测性在多智能体系统里是刚需。

**坑五：假协作。** 多个 Agent 表面上在协作，实际上 Orchestrator 已经把所有决策都做好了，其他 Agent 只是执行格式化输出。这种"多智能体"没有价值，只是增加了成本。判断标准是：如果去掉某个 Agent 用一段固定代码替代，效果没变化，那这个 Agent 就是多余的。

## 何时不该用多智能体

以下情况单智能体更合适：

- 任务步骤少于 3 步，且步骤明确
- 延迟要求严格（多 Agent 的串行调用会显著增加延迟）
- 成本高度敏感
- 任务本身不需要多视角（比如简单的信息查询、格式转换）
- 团队还没有可靠的评估手段（无法判断多 Agent 是否真的更好）

**务实的建议**：先把单 Agent 做到它的效果上限，测出指标。然后只在明确知道"单 Agent 的哪个瓶颈"的情况下，针对性地引入第二个 Agent。不要因为多智能体听起来先进就上多智能体——它的复杂度成本是真实存在的。
