# ReAct 范式：推理与行动的协同

ReAct 是 Reasoning + Acting 的缩写，由 Shunyu Yao 等人在 2022 年的论文《ReAct: Synergizing Reasoning and Acting in Language Models》中提出。它让语言模型在推理和工具调用之间交替进行，是目前构建 AI Agent 最主流的范式。

## 为什么需要 ReAct

单纯的推理（Chain-of-Thought）有一个根本局限：模型的推理完全依赖参数里的知识，一旦知识不足或过时，它不会去查，只会基于错误前提继续推理，最终产生看似合理实则错误的答案。这被称为"幻觉链条"——推理越连贯，错误越隐蔽。

单纯的行为（只调工具不推理）则缺少规划能力：不知道该调哪个工具、不知道结果是否足够、不知道什么时候停止。

ReAct 的核心洞察是：**推理和行动应该交替进行**。推理帮助决定下一步做什么动作，动作的结果反过来修正后续推理，形成一个闭环。

## 基本循环结构

ReAct 的标准形式是：

```
Question: 用户的问题
Thought: 我需要先了解 X，应该查询资料库
Action: search
Action Input: X
Observation: 检索到的内容……
Thought: 资料显示 A，但缺少 B 的信息，需要补充查询
Action: search
Action Input: B
Observation: 补充内容……
Thought: 现在信息足够回答问题了
Final Answer: 综合以上信息，答案是……
```

关键点在于：
- **Thought 是模型的自由推理**，不需要结构化，模型可以思考"我现在缺什么"
- **Action 必须是预先定义的工具名**，不能自由发挥
- **Observation 是环境（代码）返回的真实结果**，不是模型生成的
- **循环由模型自己决定何时结束**，通过输出 Final Answer 来终止

## 与工具调用（Function Calling）的关系

现代 LLM 普遍支持原生 Function Calling，可以直接输出结构化的工具调用请求。它和 ReAct 的关系是：

Function Calling 解决的是"**格式**"问题——让模型可靠地输出"调用哪个函数、参数是什么"，由 API 层面保证 JSON 格式正确。

ReAct 解决的是"**流程**"问题——什么时候该调用、调几次、结果够不够、什么时候停。

两者是互补的：可以用 Function Calling 来实现 ReAct 里的 Action 环节，让格式更可靠。但 ReAct 循环的控制逻辑（步数上限、结果判断、错误恢复）仍然需要自己实现。

实践中常见两种实现方式：
1. **文本解析式**：要求模型输出 `Action: xxx` 文本，用正则解析。优点是不依赖模型能力，任何模型都能用；缺点是解析容易失败，需要大量容错
2. **原生工具调用式**：用 API 的 tools 参数。优点是格式可靠；缺点是绑定特定模型服务，且调试时看不到"思考过程"的原始文本

本项目采用第一种，因为它的机制更透明，便于学习理解，而且不依赖任何特定厂商。

## ReAct 实现中的关键工程问题

**问题一：死循环。** 模型可能反复搜索同一个词，每次得到相同结果却不推进。这是最常见的失败模式。

解决方案：
- 设置最大步数上限（硬性拦截，必须做）
- 检测重复动作：如果连续两次 Action 和 Action Input 完全相同，强制中断并要求给出答案
- 在 prompt 里明确提示"如果已有信息足够，请直接给出 Final Answer"

**问题二：解析失败。** 模型不按格式输出，比如忘了写 Action、把多个步骤写在一行、用中文标签、加粗标签文本。这是文本解析式方案的主要痛点。

解决方案是编写健壮的解析器：
- 支持中英文标签别名（Action / 动作 / 工具）
- 容忍 Markdown 装饰符（`**Action**:`）
- 支持标签跨行
- 解析失败时不要抛异常崩溃，而是降级处理并把问题反馈给模型，让它重新输出

**问题三：工具参数错误。** 模型传了不存在的文件名、缺少必需参数、参数类型不对。

解决方案是在工具层做严格校验，并返回**对模型友好的错误信息**。不要返回 `KeyError: 'doc_id'` 这种堆栈信息，而要返回"缺少 doc_id 参数，请提供要读取的文档 ID，可用文档有：doc_01, doc_02"。错误信息本身就是给模型的提示，好的错误信息能让模型自我纠正。

**问题四：上下文膨胀。** 随着循环进行，历史 Observation 不断累积，prompt 越来越长，成本和延迟上升，且早期信息会干扰判断。

解决方案：
- 对 Observation 做截断，只保留关键部分
- 只保留最近 N 轮的完整轨迹，更早的用摘要代替
- 把工具返回的大结果存到外部（比如黑板上），prompt 里只放引用 ID

**问题五：错误累积。** 早期一步判断错误，后续所有推理都建立在错误基础上。

解决方案是引入反思机制：在给出最终答案前，让模型检查一遍"我的结论有没有依据"。这正是多智能体架构里 Critic 角色的价值。

## ReAct 与其他 Agent 范式的对比

**Plan-and-Execute**：先一次性制定完整计划，再逐步执行。优点是全局视角好、执行阶段不需要反复调 LLM（快且便宜）；缺点是无法根据中间结果调整计划。适合步骤明确、可预先规划的任务。ReAct 适合探索性强、需要根据反馈调整的任务。

**Reflexion**：在 ReAct 基础上增加自我反思环节——任务失败后，模型总结失败原因并存入记忆，下次尝试时参考。适合可重试的任务。

**Tree of Thoughts**：同时探索多条推理路径，用搜索算法（BFS/DFS）选择最优。效果更好但成本是数倍增长。适合有明确正确性判据的推理任务（比如数学题）。

**多智能体协作**：多个 Agent 各自扮演不同角色（调研、分析、写作、审校），通过共享状态协作。它不是在单个 Agent 内部改进，而是从组织架构层面提升。ReAct 是多智能体的基础构件——每个 Agent 内部通常就是一个 ReAct 循环。

## 实践建议

**从简单开始。** 不要一上来就做多智能体。先做一个单 Agent + ReAct，跑通后再拆分成多个角色。很多任务单 Agent 就够了，多智能体带来的复杂度和成本是实实在在的。

**工具设计比 prompt 设计更重要。** 工具名要自解释（`search_local_docs` 比 `q1` 好），参数要少，返回值要结构化且带足够上下文。一个设计良好的工具集能让 Agent 的成功率大幅提升。

**可观测性是必需品，不是奢侈品。** Agent 的失败往往难以复现和定位。必须记录每一步的 Thought / Action / Observation 完整轨迹，否则调试会变成猜谜。这也是本项目专门实现轨迹记录器的原因。

**永远假设模型会输出格式错误。** 所有解析逻辑都要有容错和降级路径。在生产环境里，模型输出格式错误是常态而非异常。

**给循环设置硬性上限。** 步数上限、token 上限、时间上限、成本上限，一个都不能少。没有上限的 Agent 循环是一个随时可能烧钱的隐患。
