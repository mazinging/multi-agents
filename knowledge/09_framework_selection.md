# RAG 与 Agent 框架选型

本文对比主流框架，并给出"是否该用框架"的判断依据。

## 框架能提供什么

**编排能力**：把切块、检索、生成等步骤串起来，用声明式的方式描述流程（比如 LangChain 的 LCEL 表达式）。

**组件生态**：文档加载器（支持 PDF、Word、网页、Notion 等几十种格式）、各种向量库的适配器、各种 LLM 的适配器、大量预置的 prompt 模板。

**Agent 运行时**：ReAct 循环、工具调用、记忆管理的现成实现。

**可观测性**：LangSmith、Langfuse 等配套工具，能可视化追踪每一步。

对于快速验证想法，这些能力确实能省下大量时间。一个基本的 RAG 问答，用 LangChain 可能 30 行代码就完成了。

## 主流框架对比

| 框架 | 定位 | 优势 | 劣势 |
| --- | --- | --- | --- |
| LangChain | 通用编排 | 生态最全、组件最多、社区最大 | 抽象层数多、版本迭代快、调试困难、隐藏细节 |
| LlamaIndex | RAG 专用 | 检索策略丰富（父子块、自动检索等）、文档处理强 | 也有较厚的抽象、部分高级特性需付费 |
| Haystack | 生产级 pipeline | 架构清晰、组件可替换、文档质量高 | 生态相对小、学习曲线较陡 |
| DSPy | 提示词编译 | 用编程方式优化 prompt，不用手调 | 范式较新、需要一定学习成本 |
| 原生实现 | 自己写 | 完全可控、无隐藏行为、依赖少、易调试 | 开发慢、需要自己处理所有边界情况 |

## 学习和生产的不同选择

**学习阶段：强烈建议手写。** 理由如下。

框架把关键流程都封装了。你用 LangChain 写 `retriever.get_relevant_documents(query)`，一切正常，但当效果不好时你完全不知道该从哪里查：是切块问题？embedding 问题？还是检索算法的问题？因为整个链路是黑盒。

自己实现一遍，你会确切知道：切块时边界怎么处理的、相似度怎么算的、top-k 怎么选的、prompt 怎么拼的。有了这些理解，之后无论用不用框架，你都知道该调什么。

**生产阶段：视团队情况而定。**

如果团队对框架有深入理解，用 LangChain 可以加快开发速度。但要接受它的抽象泄漏问题——遇到 bug 时可能需要读框架源码。

如果团队追求稳定可控，或者业务逻辑比较特殊（框架的抽象模型套不上），建议用"轻框架"或者自研薄封装。很多公司在初期用 LangChain 快速验证，上线时重写为原生实现，这是一个很常见的路径。

## 混合策略：取框架之长

一个务实的做法是**分层使用**：

- **文档加载层用框架**：处理 PDF、Word、HTML 的解析非常琐碎（尤其是 PDF 的表格提取），这部分用现成工具（如 `unstructured`、`pypdf`、`markitdown`）比自己写划算得多
- **切块和检索层自己写**：这是效果的关键环节，需要完全可控才能调优
- **LLM 调用层自己写薄封装**：代码不多，但能避免被框架的版本变更影响，也便于加自己的重试、缓存、成本统计逻辑
- **Agent 循环自己写**：核心控制流（步数限制、错误恢复、轨迹记录）最好自己掌控

这样既省了琐碎工作，又保住了关键环节的可见性。

## 手写实现的隐藏成本

选择自研也要清楚代价：

**文档解析**是最耗时的部分。PDF 里的表格、双栏排版、扫描件、页眉页脚，每一种都需要专门处理。如果业务文档格式复杂，这部分工作量可能超过整个 RAG 逻辑。

**边界情况**需要自己兜。空文档、超长文档、编码错误、特殊字符、中文标点与英文混排，这些在框架里都处理过了，自己写要一个个踩。

**性能优化**从零开始。批量处理、并发、缓存、增量更新，框架有现成的组件。

**生态适配**要自己维护。换向量库、换 embedding 模型、换 LLM，都要自己写适配代码。

## 具体建议

**如果目标是学习**：完全手写一遍。哪怕只写 500 行，理解深度也远超用框架搭 10 个项目。这是本项目的定位。

**如果要在两周内做出 Demo**：用 LlamaIndex 或 LangChain 快速搭。先验证业务价值，再考虑重构。

**如果要做生产系统**：混合策略。解析层用库，切块/检索/Agent 循环自研。同时在设计上保持"可替换"——把 embedding、向量库、LLM 都抽象成接口，方便将来换。

**如果有特殊需求**（自定义检索算法、复杂的 Agent 协作拓扑、严格的性能要求）：直接自研，框架的抽象会成为阻碍。

## 一个判断标准

问自己一个问题：**当系统效果不好时，我能不能准确定位到是哪一环出了问题？**

如果答案是不能，说明抽象层次太厚了，需要拆开看。无论用不用框架，可观测性都是必须的——每一步的输入输出、中间结果、耗时都要能看到。这也是为什么很多团队即使使用框架，也会在关键节点插入自己的日志和追踪。

框架不是不能用，但不能"用了就不懂"。技术选型时，团队对它的理解程度应该是一个重要权重。
