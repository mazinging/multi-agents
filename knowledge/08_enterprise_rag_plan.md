# 企业知识库问答系统落地方案

本文面向"要在企业内部落地一个中文知识库问答系统"的实际场景，给出从零到上线的完整方案。

## 需求澄清是第一优先级

企业内部知识库问答的需求描述通常很模糊："把公司的文档都灌进去，让员工能问问题。" 这个描述里缺少关键信息，直接开工必然返工。

必须澄清的问题清单：

**知识范围是什么？** 是全部文档，还是特定部门（HR 制度、产品手册、技术文档）？不同来源的文档质量差异巨大，扫描版 PDF 需要 OCR，老旧的 Word 文档格式混乱。

**用户规模是多少？** 100 人内部使用和 10000 人使用，架构完全不同。前者单机部署足够，后者需要考虑并发、缓存、限流。

**延迟要求是什么？** 交互式问答通常要求 2 秒内首字返回。如果是批量处理任务则宽松得多。

**能否出内网？** 这个问题的答案直接决定能否使用商业 API。金融、医疗、政务类企业通常强制要求内网部署。

**有多少预算？** 包括硬件（GPU、内存）和 API 调用费用。这个约束会直接影响 embedding 和 LLM 的选型。

**准确率要求多高？** 内部知识问答容错空间比对外客服大。如果答错代价高，就需要更严格的防幻觉机制和人工兜底。

## 推荐架构（中等规模：500 人以内，数据不出内网）

**文档处理层**：定时任务扫描文档目录或从 Confluence / 语雀 / 飞书拉取内容，做格式转换和清洗，然后切块。建议按文档类型走不同的切块策略（见切块策略文档）。

**存储层**：PostgreSQL + Pgvector。选择理由是在这个数据量级（通常几十万到几百万块）下，Pgvector 的 HNSW 索引性能完全够用，而且能复用企业已有的 PostgreSQL 运维体系。如果企业已有 Elasticsearch，也可以直接用它的向量字段，避免引入新组件。

**模型层**：
- Embedding：`bge-base-zh-v1.5`（768 维，CPU 上单条约 30 毫秒），或者有 GPU 时用 `bge-large-zh-v1.5`
- LLM：如果允许调 API，用国内厂商的中文模型；如果必须内网，部署 Qwen2.5-14B 或同级别的开源模型
- Rerank：`bge-reranker-base`，加上它通常能带来 10 个点以上的准确率提升

**应用层**：检索 → rerank → 组装配 prompt → 生成 → 引用校验 → 返回。加上对话历史管理和用户反馈收集。

**前端**：建议直接集成到企业已有的 IM 工具（钉钉、飞书、企微），用户学习成本最低，使用率最高。单独做一个 Web 页面的话，实际使用率往往远低于预期。

## 分阶段实施路线

**第一阶段：验证可行性（2~3 周）**

选一个范围明确的场景（比如"产品使用手册问答"），做端到端的最小可用版本。目标不是效果好，而是验证技术路线能跑通，并测出一个基线指标。

关键动作：
- 收集 100~200 篇有代表性的文档
- 搭建最小评估集：50~100 个真实问题 + 人工标注的正确答案
- 跑通链路，记录 Recall@5 和回答准确率基线

这个阶段的产出是一个能演示的 Demo 和一份基线报告。

**第二阶段：效果优化（3~6 周）**

在基线之上逐项优化，每次只改一个变量并测量效果：
- 优化切块策略（通常收益最大）
- 加入 rerank（收益稳定且实现简单）
- 尝试查询改写和多查询扩展
- 优化 prompt，特别是加上"资料不足时明确说明"的指令
- 评估是否需要混合检索（关键词 + 向量）

目标是让准确率达到可用水平（通常 75% 以上用户认为回答有帮助）。

**第三阶段：工程化（4~8 周）**

- 增量索引：文档更新后只重建变化的部分，不做全量重算
- 缓存：相同或相似问题的结果缓存，能显著降低成本和延迟
- 权限控制：不同部门只能检索到自己有权限的文档。这是企业场景的硬需求，必须在检索层做过滤而不是在展示层隐藏
- 监控：记录每次问答的检索结果、生成内容、用户反馈，便于持续发现badcase
- 反馈闭环：提供"这个回答有帮助吗"的按钮，收集真实使用数据用于优化评估集

**第四阶段：持续迭代**

用积累的真实反馈扩充评估集，定期（比如每月）跑一遍全量评估，发现指标下降及时排查（常见原因是新接入的文档质量差，污染了索引）。

## 企业场景的特殊注意事项

**权限隔离是硬需求。** 员工 A 不能通过提问获取到员工 B 部门或薪酬相关的文档内容。这个必须在检索阶段过滤（在 SQL 或向量查询里加权限条件），不能只在 UI 层隐藏答案——因为模型可能已经把内容写进回答里了。权限元数据要在文档入库时就打好标签。

**文档时效性。** 企业文档经常有多个版本，旧版本如果没有及时下架，会导致模型引用已废止的规定。需要维护文档的生命周期状态，检索时只查有效文档，并在回答里标注文档的生效日期。

**表格和附件的处理。** 企业文档里大量关键信息在表格和附件里（比如报销标准表、产品参数表）。这些内容按常规切块会失效，需要专门处理（整表成块 + 表头补全）。

**专有名词和内部术语。** 企业内部有大量缩写和黑话，通用 embedding 模型不认识。解决方案包括：维护一个术语同义词表，在检索前做查询扩展；或者在领域语料上微调 embedding 模型（成本较高，一般最后才考虑）。

**兜底策略必须明确。** 当检索不到相关内容、或模型表示资料不足时，应该返回什么？推荐做法是明确告知"知识库中未找到相关信息"，并给出可能的联系人或知识库入口，而不是让模型硬答。

## 成本估算参考

以 50 万文档块、日均 2000 次问答的中型企业为例：

**一次性成本**：索引构建。50 万块 × 平均 300 字符 = 1.5 亿字符。用 bge-base 在 GPU 上处理，约需 2~3 小时；如果用 API，按 embedding 单价折算约几十到几百元。

**存储成本**：50 万 × 768 维 × 4 字节 ≈ 1.5 GB 向量，加上 HNSW 索引约 3 GB，加上原文和元数据约 2 GB，总计 5~8 GB。这点存储在 PostgreSQL 里几乎可以忽略。

**日常推理成本**：每次问答 = 1 次 embedding（可忽略）+ 1 次 rerank + 1 次 LLM 生成。主要成本在 LLM 生成，单次约 2000 输入 token + 500 输出 token。如果用 API，2000 次/天大约每月几百到几千元，取决于模型单价。如果自部署，主要是 GPU 机器的固定成本。

**关键结论**：中等规模的企业知识库问答，成本大头是 LLM 推理，向量检索部分（存储 + 检索）的成本占比很小。所以选型时不必为了省向量库的钱而牺牲运维便利性。

## 效果预期管理

要向业务方明确预期：RAG 系统不是万能的。实际落地中：

- 文档质量好的领域（结构清晰、术语统一），准确率可以到 85% 以上
- 文档混乱的领域（大量扫描件、格式不一、内容过时），可能只有 50~60%
- 需要跨多篇文档综合推理的问题，效果明显差于单文档事实型问题
- 涉及数值计算、精确统计的问题，RAG 基本做不了，需要接工具或数据库查询

**在项目启动时就设定合理的验收标准**，避免后期因为预期不一致产生争议。建议按问题类型分类设定指标，而不是给一个笼统的整体准确率。
