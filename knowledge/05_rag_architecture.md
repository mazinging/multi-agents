# RAG 系统架构与防幻觉机制

本文说明 RAG 的完整链路设计，以及如何通过架构手段抑制幻觉（hallucination）。

## RAG 的两阶段架构

RAG 系统分为离线索引和在线检索两个阶段。

**离线索引阶段**（可离线跑，不需实时）：
1. 文档采集：从各种数据源（文件系统、数据库、API）拉取原始文档
2. 文档解析：PDF、Word、HTML 转成纯文本，表格和图片单独处理
3. 切块：按策略切成可检索单元
4. 向量化：调 embedding 模型把每个块转成向量
5. 入库：向量 + 原文 + 元数据一起写入向量库

**在线检索阶段**（必须低延迟）：
1. 查询改写：把用户的口语化问题改写成适合检索的形式（可选但很有效）
2. 查询向量化：用同一个 embedding 模型编码查询
3. 检索：向量库返回 top-k 相似块
4. 重排序（Rerank）：用交叉编码器对 top-k 精排（可选但效果显著）
5. 上下文组装：把检索结果拼进 prompt
6. 生成：LLM 基于上下文作答，并标注引用
7. 后处理：校验引用是否有效，过滤无据内容

## 查询改写：一个被低估的环节

用户的问题往往不适合直接检索。比如"我们预算不多，想做知识库问答，用啥好"，直接检索可能匹配不到好结果，因为这个词组在文档里不存在。

常见改写手段：

**HyDE（Hypothetical Document Embeddings）** 让 LLM 先假想一个答案文档，然后用这个假想文档去检索。原理是"答案和答案的相似度高于问题和答案的相似度"。实测效果好但增加一次 LLM 调用。

**多查询扩展（Multi-Query）** 让 LLM 把一个问题改写成 3~5 个不同角度的子查询，分别检索后合并去重。能覆盖更多召回路径，代价是多几次检索。

**关键词抽取** 从问题里抽出核心术语，用于混合检索中的关键词一路。

**指代消解** 多轮对话中，"它怎么样"这类问题需要结合上文补全成"Milvus 的运维复杂度怎么样"。不做消解会导致检索完全失效。

## 重排序（Rerank）的价值

向量检索用的是双编码器（bi-encoder）：查询和文档分别编码，最后算向量相似度。优点是快（文档向量可以预先算好），缺点是查询和文档之间没有交互，精度有限。

交叉编码器（cross-encoder）把查询和文档拼在一起送进模型，能做细粒度的词级交互，精度显著更高，但无法预计算，每对查询-文档都要跑一次推理，慢得多。

所以标准做法是两阶段：先用向量检索快速从百万条里召回 top-100，再用 cross-encoder 精排取 top-5。这样兼顾了速度和精度。

常用的 rerank 模型有 `bge-reranker-large`、`bge-reranker-v2-m3`、Cohere Rerank。实践数据是：加入 rerank 后，最终答案准确率通常提升 10~20 个百分点，是回报很高的优化。缺点是增加 50~200 毫秒延迟。

## 防幻觉的架构手段

幻觉指模型生成了没有依据的内容。RAG 本身就是为了抑制幻觉，但如果实现不当，模型仍然会编造。以下是几个关键的架构手段。

**第一，给可引用的锚点。** 不要只是把文本堆进 prompt，而是给每段资料编号：

```
[资料1] (来源: doc_03#2) 内容……
[资料2] (来源: doc_05#0) 内容……
```

然后在 system prompt 里明确要求"引用时标注 [资料N]"。这样模型有了明确的引用目标，编造的成本变高。

**第二，显式允许"不知道"。** 这是最容易被忽略却最重要的一条。必须在 prompt 里明确写："如果提供的资料不足以回答问题，请直接说明资料不足，不要根据常识推测。" 如果不写这句话，模型面对资料缺失时会倾向于用自己的先验知识补全，产生幻觉。给它一个"说不知道"的出口，是成本最低的防幻觉手段。

**第三，引用校验（citation verification）。** 生成完成后，程序化地检查：模型引用的每个 [资料N] 是否真实存在？引用的资料里是否真的包含相关表述？可以用简单的关键词重叠检查，也可以再调一次 LLM 做判断。校验不通过的结论应该被标记或删除。

**第四，设定检索分数阈值。** 如果检索结果的最高相似度都低于阈值（比如 0.3），说明知识库里根本没有相关内容。这时应该直接告知用户"知识库未覆盖此问题"，而不是硬把低分资料喂给模型让它编。这个判断必须在检索层做，不能指望模型自己发现资料不相关。

**第五，要求结论附带来源。** 输出格式上要求每条关键结论后面必须跟来源标注。没有来源的结论在渲染时高亮警告。这既是给用户的透明度，也是给开发者的调试信号。

## 评估 RAG 系统的指标

分为检索质量和生成质量两大类。

**检索侧指标**：
- Recall@k：正确答案是否出现在前 k 个结果里。这是最核心的指标
- MRR（Mean Reciprocal Rank）：正确结果的排名倒数的均值，衡量"排得够不够靠前"
- Context Precision：召回的块里有多少是真正相关的（衡量噪音比例）

**生成侧指标**：
- Faithfulness（忠实度）：回答是否完全基于提供的上下文，有没有编造
- Answer Relevance：回答是否切题
- Citation Accuracy：引用标注是否准确对应

工具方面，RAGAS 是常用的开源评估框架，可以自动计算上述指标。也可以用 LLM-as-Judge 的方式，让另一个模型来打分。

**没有评估就没有优化。** 很多团队花大量时间调 prompt，却从没测过 Recall@5 是多少，结果是在错误的方向上使劲。建议项目启动阶段就搭一个最小评估集（100 个问答对），后续每次改动都跑一遍。

## 常见架构反模式

**把所有文档无差别塞进上下文** 看似"信息充分"，实则稀释注意力。研究表明，上下文里噪音越多，模型对关键信息的利用能力越差（"lost in the middle"现象）。

**只做向量检索不做关键词检索** 会漏掉专有名词、型号、编号类的精确匹配。

**检索 top-k 设太大** k=20 塞进去几万字，成本高且效果反而下降。通常 k=3~5 配合 rerank 的效果优于 k=20 不用 rerank。

**忽略元数据过滤** 多租户、多知识库场景不做过滤，会召回到别的租户的数据，既是效果问题也是安全问题。
